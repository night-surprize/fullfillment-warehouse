# Складские операции

## Обновление базы

Если уже применены миграции 01-05, последовательно выполни
`06_operations.sql`, `07_document_rules.sql`, `08_analytics.sql`
и `11_demo_generator.sql`. Каждый файл выполняется один раз, целиком,
с включенным автоподтверждением.

Файлы 09 и 10 содержат отчеты и просмотр планов запросов; их можно повторять.
Если миграции 06-08 и 11 уже применялись, запускать их заново не нужно.

## Приемка

Создай документ в `receipts` и его позиции в `receipt_items`
с ожидаемым количеством, затем вызови:

```sql
CALL warehouse.start_receipt(1, 7);
CALL warehouse.receive_receipt(1, 7, '[
  {"item_id":1,"accepted":98,"damaged":2,"cell_id":101,"damaged_cell_id":301}
]'::jsonb);
```

Замени ID на значения существующих записей. Каждая позиция должна присутствовать
ровно один раз. Годный товар размещается в приемке или основном хранении,
брак - в зоне брака. Ожидаемое и полученное количество могут различаться.

Проведение выполняется целиком в одной транзакции, повторный вызов отклоняется.
Для возврата нужен сортировочный центр. Исходная отгрузка необязательна,
но если она указана, то должна быть отправлена и относиться к тому же продавцу
и центру.

Статусы приемки: `created -> expected -> receiving -> received`.
Этап `expected` можно пропустить. До проведения разрешена отмена через
`UPDATE receipts SET status='cancelled'` с условием для нужного документа.
Товары должны принадлежать продавцу документа.
Завершенный документ и его позиции изменить нельзя.

## Отгрузка

Создай документ в `shipments` и позиции в `shipment_items`, затем вызови:

```sql
CALL warehouse.confirm_shipment(1);
CALL warehouse.pick_shipment(1,7,'[
  {"item_id":1,"from_cell":101,"to_cell":201,"quantity":5}
]'::jsonb);
CALL warehouse.pack_shipment(1);
CALL warehouse.dispatch_shipment(1,7);
```

Сборка перемещает товар из хранения в упаковку. Для одной позиции можно
использовать несколько маршрутов, но сочетание позиции, исходной
и конечной ячеек должно быть уникальным.

Допускается частичная отгрузка: по документу нужно собрать хотя бы одну единицу,
а по каждой позиции - не больше запрошенного количества.
При отправке списывается все собранное. Неисполненная часть запроса остается
видна в закрытом документе и не создает следующую отгрузку автоматически.
Подтверждение не резервирует товар; нехватка остатка прерывает операцию.

Статусы: `created -> confirmed -> picked -> packed -> shipped`.
Отмена допускается в `created` или `confirmed` до начала фактической сборки.

## Генерация данных

```sql
CALL warehouse.generate_demo_data(5000,0.42);
```

Другой вариант: установи зависимости из `python/requirements.txt`,
задай `DATABASE_URL` и выполни:

```powershell
python python/generate_data.py --cycles 5000 --seed 0.42
```

Каждый запуск добавляет отдельный набор с префиксом транзакции:
20 продавцов, 200 товаров, 600 ячеек, одного сотрудника и один центр.
Для 5000 циклов создаются 5500 приемок, 5000 отгрузок, 5000 заданий сборки,
20 500 движений, а также позиции документов и аудит.
Каждый десятый цикл включает возврат. Существующие данные не очищаются.

Параметр `seed` управляет случайными значениями. ID и префиксы между запусками
различаются. Для большого проверочного набора вместимость ячеек
намеренно задана с запасом.

Даты создания охватывают 30 дней. Время обработки и отправки относится
к фактическому запуску генератора. Он не моделирует историческое распределение
длительности операций, поэтому скорость пакетного запуска не отражает
реальную скорость работы склада.

## Отчеты и проверки

В `09_analytical_queries.sql` есть рейтинг продавцов по объему,
среднее число созданных отгрузок за семь дней с учетом пустых дней,
рекурсивные адреса хранения, расхождения приемки, доля брака и загрузка ячеек.

`v_stock_ledger` показывает накопительный остаток через оконный `SUM`.
`v_inventory_reconciliation` должен возвращать пустой результат,
если остатки проводились через предусмотренные процедуры.

После генерации выполни `tests/04_workflow_test.sql`
и `tests/05_edge_cases_test.sql`. Второй тест откатывает свои добавления.
После миграции 06 используй актуальную версию теста 03.
`tests/run_integration.py` применяет миграции в пустой базе,
указанной в `TEST_DATABASE_URL`, и отказывается запускаться,
если схема `warehouse` уже существует.

`10_explain.sql` сравнивает фактические планы и обращения к буферам
для очередей продавцов и истории товара. В одном сравнении индексные
сканирования временно отключаются. Время зависит от объема данных,
состояния кеша и машины.

## Границы проекта и одновременные операции

Все процедуры проведения перед изменением остатков берут одну
транзакционную рекомендательную блокировку. Вызовы выполняются последовательно
до `COMMIT` или `ROLLBACK`. Такое решение упрощает проверку согласованности,
но ограничивает пропускную способность. Нагрузочных тестов с несколькими
подключениями пока нет.

Журнал движений и аудит запрещают `UPDATE` и `DELETE` строк.
Аудит сохраняет JSON до и после изменения, пользователя БД и ключ строки
для документов, позиций, сборки и остатков. Поле `employee_id` общего аудита
остается `NULL`; сотрудник указан в записях самих операций.

Владелец базы может менять `inventory` напрямую и отключать триггеры.
Внутренняя функция `post_stock` и процедуры не заменяют разграничение прав;
отдельная ограниченная роль приложения не настроена.
`TRUNCATE` остается командой обслуживания владельца и не перехватывается
триггерами строк. Для изменения остатков используй описанные процедуры.
Для инвентаризации есть только таблицы; проведение не входит
в реализованный цикл приемки и отгрузки.
