# Фулфилмент-склад на PostgreSQL

База данных склада, который хранит товары нескольких продавцов. Проект
охватывает приемку, хранение, сборку, упаковку и отправку на сортировочный
центр. Возвраты проходят через тот же процесс приемки.

Основная задача проекта - согласованно менять остатки и историю движений,
даже если операция завершается ошибкой на середине. Процедуры обновляют
обе части в одной транзакции, а триггеры проверяют статусы документов
и запрещают менять завершенные приемки и отгрузки.

## Быстрый запуск

Нужны PostgreSQL 16 или новее и `psql`. Проект разрабатывался на PostgreSQL 18
под Windows. Python 3.10+ нужен только для дополнительных скриптов генерации
и автоматической проверки. Демонстрационный пример выполняется целиком на SQL.

Создай пустую базу, владельцем которой является твой пользователь,
открой терминал в корне репозитория и выполни:

```powershell
psql -h localhost -U warehouse_user -d fulfillment_warehouse -f scripts/install.sql
psql -v ON_ERROR_STOP=1 -h localhost -U warehouse_user -d fulfillment_warehouse -f examples/demo.sql
```

Если `psql` не найден, смотри [инструкцию для Windows](docs/setup.md).
Установщик останавливается при первой ошибке и отказывается работать,
если в базе уже есть схема `warehouse`. Существующие объекты он не удаляет.

Пример принимает 100 единиц товара, отделяет две бракованные, перемещает
десять единиц в другую ячейку и отгружает пять из восьми запрошенных.
В конце проверяет остатки и откатывает все добавленные им данные.

## Что реализовано

- 16 таблиц с внешними ключами, проверками количества и уникальными бизнес-ключами.
- Приемка от продавцов, возвраты, перемещения и частичные отгрузки.
- Сборка товара из хранения в упаковку и последующая отправка.
- Проверка вместимости ячеек по весу и объему; в одной ячейке хранится один артикул.
- Переходы статусов, запрет изменения завершенных документов и аудит строк.
- Генерация данных через те же процедуры, которые проводят обычные операции.
- Представления, рекурсивные запросы, оконные функции и примеры планов выполнения.

`inventory` хранит текущие остатки, а `stock_movements` - историю их изменения.
[Представление сверки](sql/08_analytics.sql) сравнивает их и выводит только
расхождения. Для технических ID используются identity-столбцы.
Артикулы уникальны во всей базе, включая товары разных продавцов.

## Генерация большого набора данных

```powershell
psql -h localhost -U warehouse_user -d fulfillment_warehouse -c "CALL warehouse.generate_demo_data(5000, 0.42);"
psql -h localhost -U warehouse_user -d fulfillment_warehouse -f scripts/test.sql
psql -h localhost -U warehouse_user -d fulfillment_warehouse -f sql/09_analytical_queries.sql
psql -h localhost -U warehouse_user -d fulfillment_warehouse -f sql/10_explain.sql
```

Один запуск добавляет 5500 приемок, 5000 отгрузок и 20 500 движений,
а также позиции документов, задания сборки и записи аудита.
Повторный запуск добавит еще один набор. Даты создания охватывают 30 дней,
но время обработки относится к фактическому запуску генератора.
Эти данные подходят для проверки запросов, но не имитируют реальные сроки
складских операций.

Тесты проверяют вместимость, нехватку товара, откат после частичного сбоя,
частичную отгрузку, повторное проведение и изменение завершенных документов.
Дополнительно сверяют остатки с журналом. Запускай их в базе для разработки.
Тесты полного цикла рассчитаны на сгенерированные данные, где все отгрузки завершены.

## Ограничения

Проведение использует одну общую транзакционную блокировку.
Она упрощает согласованную работу с остатками, но выстраивает операции
всего склада в очередь. Подтверждение отгрузки не резервирует товар:
доступность остатка проверяется при сборке.

Пользовательского интерфейса и отдельной роли приложения нет.
Владелец базы может обойти процедуры и изменить остатки напрямую;
триггеры строк не заменяют разграничение прав доступа.
Аудит записывает пользователя БД, а движения товара - сотрудника.
Для инвентаризации созданы таблицы, но процедура проведения пока не реализована.

Завершенные приемки, отгрузки и их позиции менять нельзя.
Справочники используют мягкое удаление через `deleted_at`.
Изменение и удаление строк журнала движений и аудита запрещены.
Команды обслуживания владельца базы, например `TRUNCATE`, остаются доступны.
